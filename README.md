# 县域农产品直播带货选品质检发货售后平台

以**商品批次**为主线的全链路平台：农户/合作社提交水果、米面、菌菇、蜂蜜、腊味等农产品 → 运营选品质检（样品试吃）→ 直播排期（上架前履约检查）→ 仓库锁库锁包材 → 直播下单自动生成分温区发货任务 → 售后工单 → 农户结算 → 县域运营复盘。售后结论反向回流到下一场的选品、主播口径、预售量与县域公共品牌公告。

## 技术栈

- **前端**：Vue 3 + Vite + Element Plus + Pinia + Vue Router + ECharts
- **后端**：NestJS 10 + TypeORM（JWT 认证 + 角色权限）
- **数据库**：PostgreSQL 15（首次启动自动建表并写入演示种子数据）

## 一键启动（Docker Compose）

```bash
docker compose up -d --build
```

| 服务 | 地址 |
|---|---|
| 前端（nginx） | http://localhost:8080 |
| 后端 API | http://localhost:3000/api |
| PostgreSQL | localhost:5432（postgres/postgres，库 agri_live） |

后端首次启动时自动同步表结构并写入种子数据（7 商品 / 7 批次 / 5 场直播 / 590 笔订单 / 39 张售后工单 / 风险事件、坏果预警与结算单），无需手动初始化。

## 本地开发

```bash
# 1. 数据库（任选其一）
docker run -d --name pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=agri_live -p 5432:5432 postgres:15-alpine
# 或使用本机已有 PostgreSQL，创建数据库 agri_live

# 2. 后端（默认连 localhost:5432，可用 DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_NAME 覆盖）
cd backend && npm install && npm run build && npm start   # http://localhost:3000

# 3. 前端（vite 已配置 /api 代理到 3000）
cd frontend && npm install && npm run dev                 # http://localhost:5173
```

## 核心页面与业务闭环

1. **商品与批次**（农户）：填写产地、采摘时间、规格、库存、检测报告及有效期、保质期、冷链温区、包装耐压、可供直播批次；运营在此审核商品。
2. **选品质检**（运营）：对待选批次做样品试吃评分（1-10）与质检决策，通过即 `qc_passed`。
3. **直播排期**（运营）：选批次时自动弹出**上架前履约检查**——样品口感、检测报告有效期、采摘窗口、保质期覆盖、包装耐压、冷链可达城市、农户交货稳定性、可供库存八项对照，给出建议预售上限；创建场次含主播、脚本、承诺口径、价格、优惠券、预计销量。
4. **库存锁定**（仓储）：按直播排期锁定库存与包材（县域中心仓/前置仓），可释放。
5. **直播执行**：开播 → 模拟下单（订单自动扣库存、超预估即触发 `oversell` 风险）→ 每单自动生成发货任务（订单+批次+发货仓+物流温区+随单承诺）。
6. **发货任务**（仓储）：发货/送达/异常；冷链任务可上报**冷链车晚到**，自动生成链路风险。
7. **售后工单**（售后）：坏果、少发、物流延误、地址错误、用户拒收、口味不符六类；坏果工单可录入**用户拍照证据、到货果损形态、到货城市温度、坏果数量**；坏果工单处理后自动回算批次坏果率，超 5% 既触发 `defect_rising` 风险，又形成**坏果率异常预警**（见第 12 项）；处理后发起**反向决策**（继续/暂停农户、调整主播口径、降低预售量、发布品牌风险说明——后者自动生成公告草稿）。
8. **农户结算**：直播结束后按 `供货价 × 销量 − 农户承担扣减` 生成结算单，运营打款；坏果类赔付按定责结果拆分——认定农户采摘成熟度过高的部分从结算扣除，包装承压/物流温区等由平台承担。
9. **风险中心**：超预估、少供、报告过期、冷链晚到、坏果率升高、坏果率异常预警（已冻结库存）、承诺不符等事件的知晓/处置；支持一键扫描检测报告过期批次与坏果批次。
10. **批次链路**：任一批次的时间线视图，串起选品→直播→锁库→订单→发货（出库照片/线路/温区）→售后（照片证据）→结算（农户/平台承担拆分）→风险→坏果预警定责→反向决策。
11. **复盘分析**（运营）：农户稳定性评级（稳定/观察/谨慎）、品类适合直播指数、售后原因分布、**售后对复购率的影响**（有售后记录客户 vs 无售后客户复购率对比）。
12. **坏果率异常预警**（运营/售后/仓储）：某批次坏果赔付集中出现时自动生成，闭环如下：
    - **五维归因**：按 ① 采摘批次（采摘→到货天数、成熟度）② 包装方式与耐压等级 ③ 物流线路/冷链晚到/运输温区 ④ 到货城市温度 ⑤ 用户拍照证据（磕碰压伤/过熟软烂/霉变等损伤形态分布）自动汇总并给出可疑原因。
    - **库存冻结**：预警形成即冻结同批次剩余库存（已售订单正常发货赔付；下单/锁库接口拦截）。
    - **客服优先**：自动生成「同城市·同线路·同包装」用户名单（已报损高优先，未报损但同特征的纳入预警），客服可标记跟进状态。
    - **质检复盘定责**：比对**出库照片、到货照片、物流温区**，认定包装承压问题→登记后续**更换包装**；认定农户采摘成熟度过高→登记**结算扣除对应赔付**（自动重算待打款结算单）。
    - **结案解封**：定责完成后方可结案，解除同批次剩余库存冻结。

## 异常场景演示（种子数据已内置）

- 批次 `B20260920-AP-01`：销量 260 超预估 200（oversell）+ 坏果率 5.4%（defect_rising）+ 冷链晚到 2 单；含一条**已结案坏果预警**——比对出库/到货照片与温区后认定农户采摘成熟度过高，结算扣除农户赔付 ¥105（其余非坏果退款仍由农户承担，包装/物流类由平台承担）。
- 批次 `B20261005-ST-01`（奶油草莓）：120 单已发出，武汉同城 14 单（华中冷链C线、到货 31.9℃）集中坏果，74% 为磕碰压伤、包装为低耐压普通瓦楞纸箱 → 自动形成**坏果预警（坏果率 11.7%）并冻结剩余 80 件库存**；客服名单含 14 名已报损武汉用户（P5）与 15 名同线路长沙用户（P2 预警）；运营在「坏果预警」页复盘后可认定包装承压并登记更换为「加厚泡沫托+气柱袋+耐压外箱」，结案解冻。
- 批次 `B20260910-LA-01`：检测报告 2026-10-03 已过期（report_expired）+ 主播承诺「纯手工无添加」与实际配料不符（promise_mismatch）→ 已生成品牌风险公告与「暂停该农户排播」决策
- 批次 `B20260928-KW-01`：直播中，农户预警连续降雨将少供（undersupply）

## 验证方式（本题实际执行过的验证）

在本地环境（Node 22 + PostgreSQL 15，自建临时实例 127.0.0.1:5433/agri_live）实际执行并通过：

1. **构建**：`backend: tsc 编译通过`；`frontend: vite build 通过`（新增 `DefectAlerts` 视图正常打包）。
2. **启动与种子**：后端启动自动建表并写入种子；`GET /api/analytics/overview` 返回 7 商品 / 7 批次 / 590 订单 / GMV 21521 / `openDefectAlerts=1`。
3. **坏果预警自动生成与冻结**（curl 实测）：草莓批次 `B20261005-ST-01` 种子写入后自动生成 open 预警——坏果率 11.7%（14/120）、冻结剩余库存 80 件、批次 `frozenByAlert=true`；`POST /api/orders` 对冻结批次返回 400「已因坏果预警冻结剩余库存，暂停发货下单」。
4. **五维归因**：`GET /api/defect-alerts/:id` 返回——城市维度武汉 14/14、均温 31.9℃；线路维度华中冷链C线 14 坏果/2 晚到；包装为低耐压普通瓦楞纸箱；拍照损伤形态分布（磕碰压伤 10 / 过熟软烂 3 / 霉变 1）；系统自动提示「包装承压等级低且 74% 为磕碰压伤，疑似包装承压不足」「武汉 31.9℃ 高温，疑似高温催熟」。
5. **客服优先名单**：自动生成 29 人——14 名武汉已报损用户 P5（同城市+同线路+同包装+已报损加权），15 名长沙同线路未报损用户 P2（同线路+同包装）；`PATCH /api/defect-alerts/followups/:id` 可置为已处理。
6. **出库证据登记**：`POST /api/shipping/tasks/:id/outbound-evidence` 保存物流线路/出库装车照/途中最高温（11.2℃）并在复盘明细回显。
7. **定责→换包装→结案解封**：运营对草莓预警定责「包装承压/平台/更换包装=加厚泡沫托+气柱袋+耐压外箱」→ 状态变 reviewing、农户扣减 ¥0；结案后批次 `frozenByAlert=false`、可重新下单（实测返回 201）。
8. **农户成熟度定责→结算扣赔付**：苹果批次含已结案「采摘成熟度过高」预警（扣农户 ¥105）；结算单 `#1` 应收 7280、退款总额 254.90、**农户承担 149.90（=105 坏果扣赔 + 44.90 少发等非坏果）、平台承担 105**、实付 7130.10，拆分正确。
9. **售后录入证据 + 越线再触发**：新建坏果工单可保存拍照证据/损伤形态/到货温度/坏果数；将苹果一张待处理坏果工单处理为 resolved 后，坏果率升至 5.8%，自动再生成一条 open 预警并冻结 240 件（幂等：同批次有进行中预警不重复生成）。
10. **权限与校验**：未复盘直接结案返回 400；仓储角色调用定责返回 403；非法定责枚举返回 400。
11. **批次链路聚合**：`GET /api/analytics/chain/:batchId` 含 `defectAlerts`（定责/扣赔/换包装）与 `followupStats`，结算节点展示农户/平台承担拆分。

> 说明：本工作区无 Docker 守护进程，Compose 配置按标准多阶段构建编写（backend: node20 构建+tsc 编译；frontend: node20 构建+nginx 托管并反代 /api），与本地验证通过的构建命令一致。照片证据在演示数据中以 OSS 对象键表示（如 `OSS/arrival/ST01/U1-box.jpg`），前端以芯片占位并保留 key；填入真实 `http(s)` 图片地址时直接渲染可放大预览。
